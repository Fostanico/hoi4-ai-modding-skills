# HOI4 MOD 開発の汎用ガイド

[简体中文](hoi4-modding-guide.zh-CN.md) | [English](hoi4-modding-guide.en.md) | 日本語 | [Русский](hoi4-modding-guide.ru.md) | [한국어](hoi4-modding-guide.ko.md)

AI と一緒に『Hearts of Iron IV』の MOD を制作・保守するための実践ハンドブックです。遊び方の構想を普段の言葉で伝えても、スクリプトや画面、不具合を直接指定しても使えます。史実系、架空史、キャラクター重視、システム拡張、大規模改変のどれにも当てはまり、特定の世界観や個人のディレクトリに縛られません。

各セクションの依頼例はそのまま自分の設計に書き換えて活用でき、最終的な挙動は手元のゲームバージョン・依存 MOD・セーブ環境で確かめます。3 つの Skills の内部技術資料は主に英語ですが、このユーザーガイドは 5 言語で全文を用意しています。

## 1. まずは作業環境を整える

3 つの Skills をまとめて導入し、フォルダーの相対配置をそのまま保ちます。クライアント別の手順は [インストールと共有のガイド](../../../../docs/INSTALLATION.md) を参照してください。作業を始めるときは対象 MOD を開き、プロジェクトの指示書と関連コードから読ませます。小さな変更なら関係するファイルから手を付ければ十分です。

| やりたいこと | 主力の Skill | 期待できる成果 |
| --- | --- | --- |
| アイデアから新機能やシステムを作る | `hoi4-content-builder` | 入口があり、スクリプト・素材・テキストが揃った遊べる機能 |
| スクリプト・翻訳・画面・互換処理を直す | `hoi4-pdx-modding` | 対象ビルドと既存構成に馴染むきれいな実装 |
| 不具合調査・性能改善・バージョン移行 | `hoi4-review-debug` | 根拠のはっきりした原因特定と合意範囲での修正 |

対応クライアントは依頼文から Skill を自動選択でき、決まった手順を走らせたいときは名前を直接指定できます。Skills が担うのは手順と設計の拠り所であり、ファイル編集、コマンド実行、ネットワーク、ゲーム操作はクライアントと有効な MCP サーバー（読み取り専用の `hoi4_local`、および許可時に実機検証を助ける任意導入の `hoi4_desktop`）によって決まります。

最初の依頼は次のように書くとスムーズです。

> 現在の MOD に「産業支援」ディシジョンを追加してください。政治力 50 で 30 日間の生産ボーナスを得られ、有効期間中は再実行できず、終了後にまた選べるようにします。AI は戦時中だけ検討します。既存の依存関係と対応言語を維持し、関連するプロジェクト資料とバニラの書き方を確認してから実装し、変更ファイルの静的検証まで進めてください。ゲーム起動とコミットはまだ不要です。

数値や条件は自分の企画に合わせて自由に差し替えてください。具体的な PDX 構文は AI が手元のビルドを確認して組み立てます。

## 2. 検証できる振る舞いとして伝える

小さな要望は数行で足ります。大きめの機能では、コードから読み取れない判断材料を補足すると手戻りが減ります。

| 項目 | 伝えておくと助かること |
| --- | --- |
| 目的 | 新規 MOD、既存機能の変更、実現可能性の調査、読み取り専用レビュー |
| 環境 | プロジェクトの場所、対象ビルド、関係 DLC、依存 MOD と実際のロード順 |
| プレイヤーの導線 | 入口、画面に表示される内容、操作と結果、閉じ方 |
| ルール詳細 | コスト、条件、効果、期間、失敗・取消・再実行の扱い |
| 状態の持ち主 | どの国家や対象に紐づくか。画面を閉じた後・ロード後・新規開始時の動き |
| AI と互換性 | AI が使う条件、既存セーブやマルチプレイへの対応方針 |
| 素材と言語 | 原本の所在、利用許可、画面イメージ、対応言語 |
| 作業の境界 | 触ってよいファイル、ゲーム起動の可否、コミット・公開の範囲 |

「まず分析だけ」「この不具合だけ修正」「これ以上テストは増やさない」といった線引きは遠慮なく書いてください。停止を伝えたら AI は新しい検証や修正を止めて現状を引き継ぎます。「今の作業が終わったら停止」は、すでに走っている 1 つの区切られた処理を指します。

## 3. プロジェクトと対象ビルドを確かめる

既存 MOD を触るときは、技術資料、プレイヤー向けテキスト、実際の呼び出し経路から読み込みます。機能の本当の意味は、変数名やファイル名から推測するより利用側とテキストを見た方が確実です。

構文やインターフェースは対象のゲーム導入環境で裏を取ります。現在のバニラファイルと同梱ドキュメント、検証済みテンプレート、実際に有効な依存 MOD を確認し、テンプレートが現在の利用側と食い違えば最新のバニラに合わせてテンプレート側も正します。Wiki や解説記事は調査の糸口として活かし、実装前に手元のビルドで確かめましょう。

変更に関わる `descriptor.mod`、`replace_path`、ロード順、同名定義の競合も併せて点検します。互換パッチは正確な依存バージョンと実在 ID に基づいて組み、インストール資料や実機証拠が欠ける部分は未確認として明記します。

## 4. 最小の一気通貫を先に動かす

新機能は、入口から結果まで一通り動く最小単位を最初に仕上げてから中身を膨らませます。ディシジョンなら次の流れを切れ目なく結びます。

```text
カテゴリーと入口 → 表示・実行条件 → 費用と効果 → 状態・補正 → プレイヤーへの表示
                                  ↘ ローカライズ・アイコン・AI ルール
```

イベント、国家方針、技術、装備、MIO、キャラクター、GUI、音楽にもそれぞれ固有の登録と利用経路があります。定義ファイルだけでなく、入口・アイコン・多言語・効果まで繋ぎ切って完成です。

既存処理を変更するときは、実際の呼び出し経路に沿って `ROOT`、`FROM`、国家、州、キャラクターのスコープを追い、どの対象の状態を読み書きしているか見極めます。保護条件は呼び出し元が実際に欠け得る場面やセーブ移行に必要な箇所へ絞り、接続ミスを隠す無言のフォールバックは避けます。

複雑なシステムはオフラインのルールモデルや小さなゲーム内試作から始めるのが効果的です。ただし試作にも本質的な仕組みを残してください。複数オブジェクトを扱うなら作成・検索・削除・枠の再利用まで確かめ、1 件だけの固定例で済ませません。実現可能性だけの調査では、制約・案・検証計画を提示して次の指示を待ちます。

## 5. 状態・セーブ・時間を設計する

セーブに残る変数、flag、配列、イベントターゲットには、持ち主・用途・寿命をあらかじめ定めます。構造を決める前に次の 4 点を確認しておきましょう。

- **初期化**：いつ走るか。既存セーブに途中導入しても壊れないか。再初期化で初回報酬を二重配布しないか。
- **再オープンと分岐**：画面を開き直すと続きから再開か、初期化か、表示更新だけか。失敗・取消・やり直しは別の経路か。
- **永続化とマルチ**：ロード、国家切替、ホスト離脱後も残る状態は何か。全員共有とプレイヤー固有をどう分けるか。
- **「初回」の単位**：「セーブごとに、各モード・各難易度で 1 回」ならモード別・難易度別に記録し、単一の全体フラグにまとめない。

既存セーブが参照する永続 ID は保ち、改名や意味変更には移行手順を用意します。セーブデータが覚えているのはスクリプト内の ID であり、ファイル名の変更だけでは移行されません。

UI のアニメーション時間とゲームルールの時間も切り分けます。日・時間・クリック・明示ステップは一時停止や速度変更の影響がそれぞれ異なります。必要な複雑さに合わせて状態機械、イベント駆動更新、上限付き分割処理を選び、普通の機能は素直なスクリプトで簡潔に保ちます。

## 6. GUI・シェーダー・素材

画面の依頼では、配置、クリック領域、更新条件、閉じ方、ルール上のフィードバックをひとまとめに伝えます。最長テキスト、対象解像度、UI スケール、重なり順、開き直し時の振る舞いまで見渡しましょう。

シェーダーにロジックを委ねるときは、スクリプト状態、カーソル座標、開くたびにリセットされる時計など、エンジンが実際に渡せる入力を先に確かめます。傾いたカードの見た目とクリック判定、装飾用地球と操作できる主マップ、ループ演出と一度きりの演出はそれぞれの仕様を確認してください。ブラウザプレビューや単独コンパイルは見た目と構文を素早く詰めるのに役立ち、実際の解析と操作感はゲーム内で確かめます。

素材は原本から加工し、出典と権利を記録します。寸法、形式、alpha、mipmap、切り抜き、余白は実際の利用先に合わせ、1 枚の基準を全体に使い回しません。DDS の非可逆再圧縮を重ねると線画が荒れるため、ファイル容量の小ささだけで選ばず画質・VRAM・利用先要件のバランスを取ります。

フレームアニメーションはコマ数、FPS、ループ、アトラス配置を決め、大判画像はテクスチャ上限とメモリに気を配ります。音楽はメインメニューとゲーム内プレイヤーで登録方法・形式・再生条件を分けましょう。改名や連番変更の際は明示的参照とエンジンの命名規則の両方を調べ、無関係な素材は触りません。

原本、抽出フレーム、プレビュー、一時変換ファイルは所定のビルド／素材置き場に整理し、配布パッケージには実行に必要なファイルだけを収めます。

## 7. 機能と同時に多言語を整える

対応するすべての言語で同じ機能とキーを揃えます。翻訳前に用語、人物名、ゲーム概念を固め、ID、変数、アイコン記号、色コード、動的プレースホルダーをそのまま保ち、開発者メモをプレイヤー向け文章に混ぜないようにします。

ファイル名、言語ヘッダー、UTF-8 BOM、字下げ、キー書式をプロジェクト規約とテンプレートに合わせます。ファイルに訳文を書いた後は、実際にどのキーを画面が読んでいるか（名称、説明、自動生成の補正文、独自 tooltip の違い）まで追いかけましょう。

新しく書いた長文や変更箇所は改行、ボタン幅、フォントの収録字を確認します。費用・条件・失敗・報酬がどの言語でも同じルールを伝えるように整え、言語切替リンク、利用ガイド、公開説明も足並みを揃えて更新します。

## 8. 性能改善とファイル整理

最適化は実際の重い箇所を突き止めてから着手します。高頻度の `on_actions`、全体走査、深いループ、頻繁に再評価される表示条件、大きなアニメーションテクスチャが主な着眼点です。状態が変わったときだけ結果が変わる処理はイベント駆動やキャッシュへ寄せ、キャッシュの破棄タイミングをはっきり決めます。

負荷を下げたいからといって、日次の仕様を無断で週次へ変えてはいけません。分割処理を使うなら進捗と 1 回の上限を管理し、元のゲーム結果とプレイヤーへの見せ方を保ちます。

同じ解析ディレクトリ・ロード規則・寿命を持つ小ファイルは機能単位でまとめ、ロード順、互換性、自動生成、保守境界のために分けているファイルはそのまま残します。ファイル数の削減は整理のしやすさと起動時の読み込みに効きます。実行中の FPS 改善を狙う場合は、実際のプロファイル結果で確認しましょう。

統合時は定義、名前空間、並び順、重複キー、リソース参照を突き合わせ、同キー異値は設計意図で判断します。ジェネレーターがある場合は同時に更新して再生成時の揺り戻しを防ぎ、手直しも必ず一次ソースへ反映します。

## 9. 再現手順と証拠から切り分ける

不具合の報告では、ゲームビルド、有効 MOD、直前の操作、期待した動き、実際の結果の 5 点を揃えます。該当時間帯のログを読み、同じ原因のメッセージをまとめて、後続の読み込みを止める構文・参照エラーから片付けます。末尾の 1 行や前回起動時の古いログ、思いつきだけで原因を決めつけず、全体の流れを追います。

ファイル横断の問題は定義から利用側へ辿り、スコープ、状態、依存関係、素材を点検します。確定した不具合、推測の手掛かり、設計上の好み、未検証の仮説を切り分け、確認できた原因に絞って直します。

ネイティブデバッグやダンプ解析は、問題解決に本当に必要でツールと許可が揃った段階で行い、個人情報も丁寧に扱います。通常のログ調査から無断でプロセス接続や全メモリ採取へ踏み込みません。

## 10. リスクに見合う検証を選ぶ

| 変更内容・証拠 | 適切なチェック | 残る確認ポイント |
| --- | --- | --- |
| 短い文章・コメント・既存テンプレートの微修正 | diff を目視し、書式とプレースホルダーを確認 | 実行時のゲーム挙動は対象外 |
| スクリプト・参照・文字コード・素材接続 | 変更ファイルの静的検証と参照追跡 | 実機でのスコープ、時序、UI の挙動 |
| オフラインモデル・Web・画像プレビュー | ルール計算、配置、画素、フォーマット確認 | ゲーム内入力、シェーダー描画、セーブ挙動 |
| 実機操作 | 指定のビルド・プレイセット・場面での観察 | 別バージョン、旧セーブ、マルチプレイ、未確認の分岐 |

壊れるリスクに応じて最小限かつ十分な確認を選び、有効な既存証拠は再利用します。小さな修正なら関連観察点 0〜3 個で足りることがほとんどです。実機確認が要るときは許可の範囲で最短のルート（起動中セッション・テストセーブ・新規開始）を選び、準備と片付けも時間予算に含めます。修正後の再確認は変更箇所に絞ります。

ゲームの起動は、静的チェックだけでは分からない疑問を確かめるために行います。操作手段がない場合や実機テストを望まない場合は「実機未検証」と明記し、必要な手動確認の入口だけ添えます。新しい変更には必ず新しい証拠を紐づけましょう。

## 11. 文書・Git・引き渡し

- **文書は役割どおりに更新する**：技術資料には現行の構造・入口・状態・互換・ビルド規約を残し、開発ログには今回の変更と検証結果を記します。小さな変更は既存の該当箇所を直せば十分です。
- **Git 操作を丁寧に分ける**：コミット前に作業ツリーとステージ差分を確認し、進行中の他作業を崩さないようにします。素材の改名、ジェネレーター、参照はセットで届けます。コミット、push、リリース作成、Workshop 公開はそれぞれ別の操作として、指示と設定済みのリモート／ブランチに従って進めます。
- **透明な引き渡しと公開資料の衛生**：完了内容、検証した範囲、未確認の挙動、Git の状態を簡潔に報告します。公開文書は汎用例と仮のパスで統一し、個人パスや特定作品のキャラクター・独自ルール・再現できない個別確認記録は混ぜず、出典とライセンスをきちんと保ちます。

## 12. そのまま書き換えて使える依頼例

**実現可能性だけ調べる**

> この MOD に進捗を保存できる経営パネルを作れるか検討してください。入力インターフェース、状態の持ち主、ロードと一時停止時の挙動、性能上の限界、最小の検証計画をまとめてください。まずは分析だけで、ファイル変更とゲーム起動はまだ行いません。

**既存機能の不具合を直す**

> このイベントを 2 回目に開くと報酬がもう一度配られます。入口、プレイヤー向けテキスト、状態の寿命をたどり、既存セーブの進捗を保ったまま重複受取を止めてください。関係する分岐だけを確認し、他の報酬数値は変えないでください。

**小ファイルを機能別に整理する**

> 最近増えた小ファイルを機能ごとにまとめ、ID・ロード順・互換境界を維持してください。ジェネレーターと参照も併せて更新し、変更前後のパス対応表と内容一致の確認結果を添えてください。ゲームルールは変えません。

**素材差し替えと多言語更新**

> この画面の背景を指定の原本へ差し替え、現在の利用先の寸法に合わせて比率を保ち、既存デザインどおりの余白を付けてください。原本は残します。対応する全言語の説明を更新し、最長文と新規素材パスを確認したうえで出力形式とチェック結果を報告してください。

**引き渡しと push の準備**

> 完了した修正を更新ノートにまとめ、実測済みと未確認の範囲をはっきり分けてください。ステージ範囲を確認してから設定済みの対象ブランチへコミット・push し、関係ないローカル変更は残します。今回はリリース作成や Workshop 公開は行いません。
