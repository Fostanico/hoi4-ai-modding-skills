# HOI4 MOD 開発の汎用ガイド

[简体中文](hoi4-modding-guide.zh-CN.md) | [English](hoi4-modding-guide.en.md) | 日本語 | [Русский](hoi4-modding-guide.ru.md)

このガイドは、AI を使って『Hearts of Iron IV』の MOD を制作・保守する方向けのものです。ゲーム内で実現したいことを普段の言葉で説明しても、スクリプト、インターフェース、不具合を直接指定しても構いません。歴史、架空史、キャラクター、ゲームプレイ拡張、大規模改変などに使える手順であり、特定の作品、国家、作者の PC 上のパスを前提にしません。

以下は再利用できる開発方法です。依頼例は、あなたのゲームバージョン、依存 MOD の組み合わせ、セーブデータで動作確認済みという意味ではありません。3 つの Skills の内部技術資料は主に英語ですが、この利用ガイドは 4 言語で全文を提供しています。

## 1. 最初にすること

3 つの Skills をまとめて導入し、相対的なフォルダー構成を維持してください。クライアントごとの導入方法は[インストールと共有の説明](../../../../docs/INSTALLATION.md)を参照してください。対象 MOD を開き、AI にプロジェクトの指示と関連コードを読ませます。小さな変更のためにプロジェクト全体を調査する必要はありません。

| 作業 | 主に使う Skill | 期待する成果 |
|---|---|---|
| アイデアから新コンテンツやシステムを制作 | `hoi4-content-builder` | 入口があり、スクリプト・素材・テキストを備えた操作可能な機能 |
| スクリプト、ローカライズ、画面、互換処理の変更 | `hoi4-pdx-modding` | 対象バージョンと既存プロジェクトに合った実装 |
| 不具合、性能、バージョン移行の調査 | `hoi4-review-debug` | 根拠のある診断と、合意した範囲での修正 |

対応クライアントは Skill を自動選択できます。名前を明示しても構いません。Skills が提供するのは手順と参考資料です。ファイル操作、コマンド、ネットワーク、ゲーム操作の可否はクライアントによります。任意のローカル MCP ツールは読み取り専用の情報を提供し、ゲームの起動や MOD の書き換えは行いません。

最初の依頼例です。

> 現在の MOD に「産業支援」ディシジョンを追加してください。政治力 50 を支払い、30 日間の生産ボーナスを得ます。有効期間中は再購入できず、終了後に再利用できます。AI は戦時中のみ利用を検討します。既存の依存関係と対応言語を維持してください。関連するプロジェクト説明とバニラの例を読み、実装と必要な静的検証を行ってください。ゲーム起動とコミットはまだ行わないでください。

数値や制約は例です。自分の設計に置き換えれば、AI が適切な実装方法を調べます。

## 2. 確認可能な動作として伝える

通常は短い依頼で十分です。大きな作業では、プロジェクトから分からない項目を補足してください。

| 項目 | 明確にする内容 |
|---|---|
| 目的 | MOD 新規制作、既存機能の変更、実現可能性の検討、読み取り専用レビュー |
| 環境 | プロジェクトの場所、対象バージョン、関連 DLC、依存 MOD、実際のロード順 |
| プレイヤーの操作 | 入口、表示内容、操作と結果、終了方法 |
| ルール | 費用、条件、効果、期間、失敗、取消、繰り返し操作 |
| 状態の範囲 | 所有する国家や対象、画面を閉じた後・ロード後・新規開始時の扱い |
| AI と互換性 | AI の利用条件、既存セーブやマルチプレイへの対応要否 |
| 素材と言語 | 原本、利用許可、見た目の要件、対応言語 |
| 作業範囲 | 変更可能な範囲、ゲーム起動、コミットや公開の可否 |

「分析だけ」「この不具合だけ修正」「追加テストは不要」といった境界を明記できます。停止を求めたら、AI は新しい検証や修正を開始せず、現在の状態を報告すべきです。「今の作業が終わったら停止」は、すでに進行している 1 つの限定された処理を意味します。

## 3. プロジェクトと根拠を確認する

既存機能では、技術説明、関連するプレイヤー向け文章、呼び出し元を先に読みます。変数名だけでゲームルールを判断したり、ファイル名だけで用途を決めたりしません。

構文とインターフェースは対象のインストールに照らして確認します。現在のバニラファイルと同梱文書、Skill のテンプレートやキット、実際に有効な依存 MOD を使います。テンプレートが現在の利用側コードと矛盾する場合は、現在の根拠に合わせて修正します。Wiki やコミュニティ資料は手掛かりになりますが、古い例を対象バージョンの動作より優先しません。

変更に関係する `descriptor.mod`、`replace_path`、ロード順、同名定義を調べます。互換パッチは正確な依存バージョンと実在する ID に基づいて作成します。インストールファイルや実行時の証拠がなければ、未確認の部分を明示します。

## 4. 入口から結果まで機能をつなぐ

まず最小限の機能を最後まで動く形にし、その後でコンテンツを増やします。ディシジョンなら、次のようなつながりが必要です。

```text
カテゴリーと入口 → 表示・利用条件 → 費用と効果 → 状態や補正 → 結果の表示
                                  ↘ 翻訳、アイコン、AI の利用条件
```

イベント、国家方針、技術、装備、MIO、キャラクター、GUI、音楽にも、それぞれ利用側とリソースのつながりがあります。定義ファイルだけを作り、入口、アイコン、文章、効果が未接続のままでは完成ではありません。

既存機能の変更では、実際の呼び出しをたどり、`ROOT`、`FROM`、国家、州、キャラクターなどのスコープを確認します。どの対象の状態を読み書きするかを明確にします。呼び出し元が実際に存在しない場合や、セーブのライフサイクル上必要な場合に保護処理を入れ、無言の代替処理で接続ミスを隠さないようにします。

複雑な機能はオフラインのルールモデルと小規模なゲーム内サンプルから始められます。ただし必要な仕組みは維持します。複数の実体を扱うなら、作成、検索、削除、空き領域の再利用を考慮します。固定の 1 オブジェクトだけでは設計全体を確認できません。実現可能性だけの依頼では、制約、選択肢、検証方法を提示し、実装の指示を待ちます。

## 5. 状態、セーブ、時間を設計する

永続的な変数、flag、配列、イベントターゲットには、所有者、目的、寿命が必要です。データ構造を選ぶ前に、次を確認します。

- 初期化はいつ行うか。既存セーブにも追加機能を初期化できるか。再初期化で報酬を再配布しないか。
- 画面を開き直すと続行、リセット、表示更新のどれになるか。失敗、取消、再開は別の経路か。
- ロード、国家切替、実行主体の消失後も有効な状態は何か。マルチプレイの共有状態とプレイヤー別状態をどう分けるか。
- 「初回達成」は何を単位にするか。「セーブごとに、各ゲームの各難易度で 1 回」なら、ゲームと難易度を別々に記録し、共通の初回フラグ 1 つで済ませない。

永続 ID と既存セーブの状態を保ちます。名称や意味を変える場合は移行を設計します。ファイル名を変えても、通常はセーブ内の識別子は移行されません。

画面のアニメーション時間とゲームルールの時間を分離します。日、時間、クリック、明示的な論理ステップは意味が異なり、一時停止とゲーム速度も考慮します。必要な複雑さに応じて状態機械、イベント駆動更新、上限付きの分割処理を使います。通常の機能のために汎用インタープリターを先に作る必要はありません。

## 6. GUI、演出、素材

レイアウト、クリック領域、更新条件、閉じ方、ルール上の結果表示をまとめて指定します。変更した長文、対象解像度、拡大率、重なり、描画順、開き直しを確認します。

シェーダーがスクリプト状態、正確なカーソル位置、画面を開くたびにリセットされる時計を自動で受け取るとは限りません。傾いたカードの見た目とクリック領域、装飾用地球と操作可能な主マップ、ループと一度だけの演出は、それぞれのインターフェースを確認します。ブラウザのプレビューや単独のシェーダーコンパイルは、ゲーム側の解析や操作を保証しません。

素材加工は原本から行い、出典と利用許可を保管します。実際の利用先に合わせて寸法、形式、alpha、mipmap、切り抜き、余白を確認し、ある画像の設定をすべてに当てはめません。DDS の非可逆再圧縮は線画を傷めることがあります。ファイルが小さいことと、画質や GPU メモリ使用量が適切であることは別です。

フレームアニメーションではコマ数、速度、ループ、アトラス配置を決め、大きな画像ではテクスチャ上限とメモリを考慮します。音楽ではメインメニューとゲーム内プレイヤーの登録、形式、再生条件を分けます。パスや連番の変更時は明示的な参照とエンジンの命名規則を調べ、他の素材内容を維持します。

原本、抽出フレーム、プレビュー、一時変換ファイルは、プロジェクトで決めた素材・ビルド用の場所に保存します。配布物には実行に必要なものを含めます。原本の保存は、すべての中間ファイルを Git に追加するという意味ではありません。

## 7. 機能設計と同時に多言語を考える

対応するすべての言語で同じ機能とキーを揃えます。用語、名前、ゲーム概念を決めてから翻訳し、ID、変数、アイコン記号、色コード、動的プレースホルダーを維持します。開発者向け指示はプレイヤーの文章に混ぜません。

言語ファイル名、言語ヘッダー、文字コード、字下げを確認し、キーの書式はプロジェクトと Skill のテンプレートに従います。ファイル内に文章があっても、目的の画面が使うとは限りません。名称、説明、自動生成される補正文、独自 tooltip は表示方法が異なる場合があります。

追加・変更した長文の改行、ボタン幅、文字表示を確認します。費用、条件、失敗、報酬が各言語で同じ意味になるようにします。言語切替、利用ガイド、公開説明も一緒に更新し、見出しだけの翻訳や古い説明を残さないようにします。

## 8. 性能とファイル整理

実際の負荷を見つけてから最適化を選びます。高頻度の `on_actions`、全体走査、深いループ、繰り返し評価する表示条件、大きな動的テクスチャに注目します。状態変化時だけ更新できる結果にはイベント駆動やキャッシュが使えますが、キャッシュを無効にする条件が必要です。

実行回数を減らすために日次の仕組みを無断で週次に変えません。分割処理では進捗と上限を管理し、結果と表示が元の設計に合うようにします。

同じ解析対象ディレクトリ、ロード規則、ライフサイクルを持つ小ファイルは、担当機能ごとにまとめます。ロード順、互換性、自動生成の担当範囲、保守上の理由がある分割は維持します。ファイル数削減は主に保守性と起動時の読み込みに役立つもので、継続的な FPS 向上の証拠にはなりません。

統合時は定義、名前空間、順序、重複キー、リソース参照を比較します。同じキーで値が異なる場合は意味を判断します。ジェネレーターも更新し、次回ビルドで旧パスを再作成しないようにします。生成物は再現可能にし、手修正は生成元にも反映します。

## 9. 再現手順と証拠から診断する

バージョン、有効な MOD、操作、期待した結果、実際の結果を記録します。該当時刻のログを読み、同じ原因の反復をまとめ、後続コンテンツを読み込めなくする解析・参照エラーを優先します。最後のログ 1 行、終了後の古いログ、単発の推測だけでクラッシュ原因を断定しません。

ファイルをまたぐ問題は定義と利用側をたどり、スコープ、状態、依存関係、素材を確認します。確定した不具合、推測的な手掛かり、設計上の好み、未検証の仮説を区別し、修正を原因に集中させます。

ネイティブデバッグやダンプ解析は、問題に必要で、ツールがあり、許可が対象操作を含む場合に行います。個人情報を適切に扱います。通常のログ調査を、プロセスへの接続、ツール導入、全メモリ採取に自動で拡大しません。

## 10. 必要十分な根拠で確認する

| 変更または証拠 | 適切な確認 | それだけでは言えないこと |
|---|---|---|
| 文章、コメント、既知テンプレートの小変更 | diff を読み、書式とプレースホルダーを維持 | すべてのゲーム動作をテストした |
| スクリプト、参照、文字コード、素材接続 | 変更ファイルの静的検証と参照確認 | ゲーム内のスコープ、時序、画面が正しい |
| オフラインモデル、Web、画像プレビュー | ルール、配置、画素、素材形式の確認 | ゲーム内入力、描画、セーブが正常 |
| ゲーム内操作 | 特定バージョン、プレイセット、場面で観察 | 他バージョン、セーブ、マルチプレイ、全分岐も正常 |

失敗リスクに応じた最小限の確認を選び、現在も有効な証拠を再利用します。小作業では通常 0～3 個の関連観察点で足ります。実機確認が必要なら、許可の範囲内で現在のセッション、テストセーブ、新規開始から最短の方法を選び、準備と片付けも時間予算に含めます。修正後は必要な対象だけを再確認します。

ゲーム起動は静的確認では解決できない疑問に答えるために行います。操作ツールがない場合やテストを希望しない場合は「実機未検証」と記し、必要な手動確認の入口を示します。過去のテストを新しい変更の証明に使いません。

## 11. 文書、Git、引き渡し

技術説明には現在の構成、入口、状態、互換性、ビルド規約を記録し、開発ログには変更と証拠を残します。小変更なら既存の該当箇所を更新し、別の文書一式を作る必要はありません。

コミット前に作業ツリーとステージ済み diff を確認し、他の作業中の変更を維持します。素材の改名、ジェネレーター、参照はまとめて引き渡します。コミット、push、リリース作成、Workshop アップロードは別の操作です。ユーザーの依頼と既存の許可に従い、実際に設定されたリモートとブランチを使います。

完了内容、検証範囲、未確認の動作、Git の状態を報告します。公開文書には汎用例と仮のパスを使い、個人のディレクトリ、プロジェクト固有のキャラクターや規則、追跡不能な個別の動作確認記録を混ぜません。出典とライセンスは適切な場所に残します。

## 12. 書き換えて使える依頼例

**実現可能性だけ調べる**

> この MOD に進捗保存付きの経営パネルを作れるか検討してください。入力インターフェース、状態の所有者、ロードと一時停止、性能上の制約、最小の検証計画を説明してください。まだファイル変更やゲーム起動はしないでください。

**既存機能を修正する**

> このイベントは 2 回目に開くと報酬を再配布します。入口、プレイヤー向け文章、状態のライフサイクルから原因を調べ、既存セーブの進捗を保って重複受取を修正してください。関連分岐だけ確認し、他の報酬数値は変更しないでください。

**ファイルを整理する**

> 最近追加した小ファイルを機能別に統合し、ID、ロード順、互換性の境界を維持してください。ジェネレーターと参照も更新し、変更前後のパス対応と必要な内容同等性の確認を示してください。ゲームルールは変えないでください。

**素材と翻訳を更新する**

> この画面の背景を指定原本に置き換え、縦横比を保って現在の利用先の寸法に合わせてください。余白は既存デザインに従い、原本を保存してください。4 言語の説明を更新し、最長テキストと新規素材パスを確認してください。出力形式と確認結果も説明してください。

**引き渡しを準備する**

> 完了した修正を更新説明にまとめ、実測と未検証を区別してください。ステージ範囲を確認して、設定された対象ブランチへコミットと push を行い、無関係のローカル変更を維持してください。今回はリリース作成や Workshop 公開はしないでください。
