# HOI4 모드 개발 가이드

[简体中文](hoi4-modding-guide.zh-CN.md) | [English](hoi4-modding-guide.en.md) | [日本語](hoi4-modding-guide.ja.md) | [Русский](hoi4-modding-guide.ru.md) | 한국어

AI와 함께 *Hearts of Iron IV* 모드를 만들고 다듬는 제작자·유지보수자를 위한 실전 핸드북입니다. 머릿속 플레이 아이디어를 일상 언어로 풀어내도 좋고, 고칠 스크립트나 UI, 버그를 바로 짚어 주어도 됩니다. 역사, 대체 역사, 캐릭터 중심, 시스템 확장, 대형 개편 모드 어디에나 그대로 적용할 수 있으며 특정 세계관이나 개인 폴더 구조에 묶이지 않습니다.

본문의 요청 예시는 내 설계에 맞게 바꿔 쓸 수 있는 틀이며, 최종 동작은 목표 게임 빌드·의존 모드 조합·세이브 환경에서 확인합니다. 세 스킬의 내부 기술 참고 문서는 주로 영어로 되어 있고, 이 사용자 가이드는 다섯 개 언어 전체로 제공합니다.

## 1. 작업대부터 갖추기

세 스킬을 한 세트로 설치하고 내부 폴더 구조를 그대로 유지하세요. 클라이언트별 설치 방법은 [설치 및 공유 안내](../../../../docs/INSTALLATION.md)에 정리되어 있습니다. 작업을 시작할 때는 대상 모드를 열어 AI가 프로젝트 안내 문서와 직접 관련된 코드부터 읽게 하면 됩니다. 작은 수정에 저장소 전체를 훑을 필요는 없습니다.

| 하려는 작업 | 주력 스킬 | 기대 결과 |
| --- | --- | --- |
| 아이디어를 새 기능이나 시스템으로 구현 | `hoi4-content-builder` | 진입점, 스크립트, 에셋, 현지화가 깔끔하게 이어진 플레이 가능 기능 |
| 스크립트·현지화·UI·호환성 수정 | `hoi4-pdx-modding` | 대상 게임 빌드와 기존 아키텍처에 맞는 정돈된 코드 |
| 결함 진단·성능 최적화·버전 이행 | `hoi4-review-debug` | 근거가 또렷한 원인 규명과 합의 범위 안의 정확한 수정 |

자동 선택을 지원하는 클라이언트는 요청 내용에 맞는 스킬을 알아서 고르며, 정해진 절차를 따르고 싶을 때는 스킬 이름을 직접 적어 호출하면 됩니다. 스킬은 작업 방식과 참고 근거를 제공하고, 파일 수정·명령 실행·네트워크·실기 조작 권한은 클라이언트와 연결한 MCP 서버(읽기 전용 로컬 취증 `hoi4_local`, 허가 시 실기 테스트를 돕는 선택형 `hoi4_desktop`)에 따라 정해집니다.

첫 요청은 이런 식으로 시작해 보세요.

> 현재 모드에 ‘산업 지원’ 결정을 추가해 줘. 플레이어가 정치력 50을 쓰면 30일 동안 생산 보너스를 받고, 효과가 유지되는 동안에는 다시 누를 수 없으며 끝나면 다시 활성화돼야 해. AI는 전쟁 중일 때만 고려해 줘. 기존 의존성은 유지하고 프로젝트가 지원하는 모든 언어를 채워 줘. 먼저 관련 프로젝트 문서와 바닐라 예제를 확인한 뒤 구현하고 변경 파일의 정적 검사를 돌려 줘. 게임 실행과 커밋은 아직 하지 마.

수치와 조건은 원하는 대로 바꾸고, 정확한 PDX 문법과 구현 방식은 AI가 설치된 게임 빌드를 확인해 결정하게 맡기면 됩니다.

## 2. 확인할 수 있는 동작으로 요청하기

간단한 작업은 두세 문장이면 충분합니다. 규모가 큰 기능일수록 코드만 봐서는 알기 어려운 설계 결정을 미리 짚어 주면 재작업이 크게 줄어듭니다.

| 항목 | 함께 적어 두면 좋은 내용 |
| --- | --- |
| 목표 | 새 모드 제작, 기존 기능 수정, 구현 가능성 검토, 읽기 전용 감사 |
| 환경 | 모드 경로, 대상 게임 빌드, 관련 DLC, 의존 모드와 실제 로드 순서 |
| 플레이어 동선 | 진입 위치, 화면에 보일 내용, 조작과 결과, 닫기·종료 흐름 |
| 규칙 세부 | 비용, 조건, 효과, 지속 기간, 실패·취소·반복 동작 |
| 상태 소유권 | 어느 국가나 객체가 보유하는지, 창 닫기·세이브 로드·새 게임 시 처리 |
| AI와 호환성 | AI 사용 조건, 기존 세이브 및 멀티플레이 호환 여부 |
| 에셋과 언어 | 원본 경로, 사용 권한, 화면 구도 요구, 지원 언어 |
| 작업 경계 | 수정 허용 파일, 게임 실행 허가 여부, 커밋·배포 범위 |

“먼저 분석만 해 줘”, “이 버그만 고쳐 줘”, “테스트를 더 늘리지 마”처럼 경계를 분명하게 적으세요. 중단을 요청하면 AI는 새 검사나 수정을 즉시 멈추고 현재 상태를 보고합니다. “지금 하는 작업까지만 끝내 줘”는 이미 진행 중인 한정된 단위 작업 하나만을 뜻합니다.

## 3. 프로젝트 맥락과 대상 빌드부터 확인하기

기존 코드를 건드리기 전에 프로젝트 기술 문서, 플레이어가 보는 현지화 문구, 실제 호출 경로를 먼저 읽습니다. 기능이 실제로 무엇을 하는지는 파일명이나 변수명을 추측하기보다 호출 코드와 플레이어 문구에서 확인하는 편이 훨씬 정확합니다.

문법과 인터페이스는 대상 설치본을 기준으로 검증합니다. 현재 버전의 바닐라 파일과 동봉 문서, 검증된 스킬 템플릿·키트, 실제로 켜 둔 의존 모드를 확인하고 템플릿과 현재 바닐라 사용처가 어긋나면 현재 사용처에 맞춰 템플릿을 고칩니다. 위키와 커뮤니티 글은 좋은 실마리로 삼되, 최종 구현은 현재 설치된 빌드에서 확인합니다.

변경과 맞물린 `descriptor.mod`, `replace_path`, 로드 순서, 중복 정의도 함께 점검하세요. 호환 패치는 정확한 의존 모드 버전과 실제 내부 ID를 대조해 작성하며, 설치 파일이나 실행 근거가 없을 때는 확인하지 못한 부분을 솔직하게 적어 둡니다.

## 4. 작은 수직 슬라이스부터 끝까지 연결하기

새 기능은 진입부터 결과까지 매끄럽게 돌아가는 최소 단위를 먼저 완성한 뒤 분량을 넓혀 갑니다. 결정 하나를 예로 들면 흐름은 다음과 같습니다.

```text
분류와 진입점 → 표시·실행 조건 → 비용과 효과 → 상태·수정치 → 플레이어 피드백
                               ↘ 현지화·아이콘·AI 규칙
```

이벤트, 국가중점, 기술, 장비, MIO, 인물, GUI, 음악도 각자의 등록과 소비 체인을 갖고 있습니다. 정의 파일만 두지 말고 진입점, 아이콘, 다국어 문구, 실제 효과까지 모두 이어야 플레이어가 쓸 수 있는 기능이 됩니다.

기존 기능을 고칠 때는 실제 호출 경로를 따라 `ROOT`, `FROM`, 국가, 주, 인물 스코프를 짚어 가며 각 효과가 어느 대상의 상태를 읽고 쓰는지 파악합니다. 방어 조건은 호출자가 실제로 비어 있을 수 있거나 세이브 이행에 꼭 필요한 곳에만 두고, 조용한 기본값 대체로 끊어진 연결을 가리지 않습니다.

복잡한 시스템은 오프라인 규칙 모델이나 작은 게임 내 프로토타입으로 시작하는 편이 안전합니다. 이때 설계의 핵심 메커니즘을 프로토타입에도 살려 두세요. 여러 객체를 다루는 기능이라면 생성·조회·삭제·슬롯 재사용을 함께 검증해야 합니다. 구현 가능성 검토만 요청받았다면 제약, 선택지, 검증 계획을 정리해 전달하고 구현 지시를 기다립니다.

## 5. 상태·세이브·시간 설계하기

세이브에 남는 변수, 플래그, 배열, 이벤트 대상은 만들기 전에 소유자·용도·수명을 정합니다. 자료 구조를 고르기 전에 아래 네 가지를 짚어 보세요.

- **초기화**: 언제 초기화하는가? 기존 세이브에 새 기능을 추가해도 안전하게 초기화되는가? 재초기화 때 일회성 보상이 또 지급되지 않는가?
- **재진입과 분기**: 창을 닫았다가 다시 열면 진행이 이어지는가, 초기화되는가, 화면만 갱신되는가? 실패·취소·재시작 경로가 분리되어 있는가?
- **지속성과 멀티플레이**: 세이브 로드, 국가 전환, 호스트 이탈 뒤에도 남는 상태는 무엇인가? 공용 상태와 플레이어별 상태를 어떻게 나누는가?
- **‘첫 완료’의 단위**: ‘세이브마다, 각 모드·난이도별로 한 번’이라면 전역 플래그 하나에 묶지 말고 모드와 난이도별로 따로 기록해야 합니다.

세이브가 기억하는 영구 ID는 안정적으로 유지하고, 이름이나 의미를 바꿀 때는 이행 절차를 함께 설계합니다. 세이브 데이터는 파일명이 아니라 스크립트 속 ID를 기준으로 연결됩니다.

UI 애니메이션 시계와 게임플레이 시계도 분리해 설계하세요. 게임의 일·시간·클릭·명시적 로직 단계는 일시 정지와 배속에 따라 다르게 움직입니다. 필요한 복잡도에 맞춰 상태 머신, 이벤트 기반 갱신, 한도를 둔 분할 처리를 선택하고, 평범한 기능은 간결한 스크립트로 유지합니다.

## 6. GUI, 셰이더, 에셋

UI 요청에는 배치, 클릭 영역, 갱신 시점, 닫기 흐름, 규칙 피드백을 함께 담아 주세요. 긴 번역문, 대상 해상도, UI 배율, 겹침·레이어 순서, 닫았다 다시 열 때의 동작을 중점적으로 살핍니다.

GUI 셰이더에 로직을 맡기기 전에는 엔진이 실제로 넘겨주는 입력(스크립트 상태, 정확한 마우스 좌표, 창을 열 때마다 초기화되는 타이머 등)을 인터페이스 기준으로 먼저 확인합니다. 기울어진 카드의 외형과 클릭 영역, 장식용 지구본과 조작 가능한 지도, 반복 애니메이션과 1회성 연출은 각각 확인 포인트가 다릅니다. 브라우저 미리보기와 셰이더 단독 컴파일은 시각·문법 점검을 빠르게 도와주며, 실제 파싱과 클릭 반응은 게임 안에서 확인합니다.

에셋 가공은 항상 원본에서 시작하고 출처와 사용 권한을 남겨 둡니다. 크기, 포맷, 알파, 밉맵, 크롭, 여백은 실제 소비 컨트롤에 맞춰 정하고 한 이미지의 설정을 전체에 일괄 적용하지 않습니다. DDS 손실 재압축을 거듭하면 선화가 뭉개지므로, 파일 크기만 줄이기보다 화질·VRAM·소비처 요구를 함께 맞춥니다.

프레임 애니메이션은 프레임 수, 재생 속도, 반복 여부, 아틀라스 배치를 미리 정하고 대형 텍스처는 VRAM과 크기 제한을 살핍니다. 음악은 메인 메뉴와 게임 내 플레이어의 등록 방식, 지원 형식, 재생 조건을 구분하세요. 파일 이름이나 번호를 바꿀 때는 명시적 참조와 엔진 명명 규칙을 같이 확인하고 무관한 에셋은 그대로 둡니다.

원본, 추출 프레임, 미리보기, 임시 변환 파일은 프로젝트가 정한 빌드·에셋 폴더에 모아 두고 배포 패키지에는 실행에 꼭 필요한 파일만 담습니다.

## 7. 기능과 함께 현지화 챙기기

지원하는 모든 언어가 같은 기능과 키를 빠짐없이 갖추도록 합니다. 번역에 앞서 용어, 인물 표기, 핵심 플레이 개념을 통일하고, ID·변수·아이콘 태그·색상 코드·동적 자리표시자를 그대로 유지하며 개발 메모가 플레이어 문구에 섞이지 않게 주의합니다.

프로젝트 규칙과 스킬 템플릿에 맞춰 파일명, 언어 헤더, 인코딩, 들여쓰기, 키 문법을 점검합니다. 한국어는 `localisation/korean/` 아래 `_l_korean.yml` 파일을 두고 첫 줄에 `l_korean:`을 적으며 UTF-8 BOM으로 저장합니다. [기본 한국어 현지화 템플릿](../../../hoi4-content-builder/assets/templates/localisation_l_korean.yml)과 [고급 한국어 현지화 템플릿](../../../hoi4-content-builder/assets/templates/localisation-advanced/localisation_advanced_l_korean.yml)을 참고하세요. 문구를 파일에 넣은 뒤에는 실제 UI가 어느 키를 읽는지(이름, 설명, 자동 생성 수정치 문구, 커스텀 툴팁 경로)까지 확인합니다.

새로 쓰거나 길어진 문장은 줄바꿈, 버튼 너비, 글꼴 글리프(커스텀 비트맵 글꼴에 한글과 문장 부호가 들어 있는지 포함)를 점검합니다. 비용·조건·실패·보상의 규칙 의미가 모든 언어에서 똑같이 전달되도록 맞추고, 언어 전환 링크·가이드·공개 소개도 함께 갱신합니다.

## 8. 성능 최적화와 파일 정리

최적화는 실제 병목을 먼저 찾고 시작합니다. 고빈도 `on_actions`, 전체 순회, 중첩 반복, 매번 재평가되는 표시 조건, 초대형 애니메이션 텍스처를 우선 점검하세요. 상태가 바뀔 때만 결과가 달라지는 로직은 이벤트 기반 갱신이나 캐시로 옮기고 캐시 무효화 조건을 명확히 둡니다.

부하를 줄이려고 매일 도는 규칙을 상의 없이 매주 규칙으로 바꾸면 원래 플레이 감각이 망가집니다. 분할 처리를 쓸 때는 진행 위치와 1회 상한을 관리하면서 원래 결과와 플레이어 피드백을 지킵니다.

같은 파서 폴더·로드 규칙·수명을 공유하는 작은 파일은 기능별로 묶고, 로드 순서·호환성·자동 생성·유지보수 경계 때문에 나눈 파일은 그대로 둡니다. 파일 수를 줄이면 폴더 관리와 시작 시 파일 읽기가 한결 깔끔해지며, 실행 중 FPS 향상 여부는 실제 프로파일링으로 확인합니다.

병합할 때는 정의, 네임스페이스, 순서, 중복 키, 리소스 참조를 대조하고 같은 키에 값이 다르면 설계 의도로 정리합니다. 생성 스크립트가 있다면 함께 갱신해 다음 빌드에서도 재현되도록 하고, 수동 수정도 반드시 원본 소스에 반영합니다.

## 9. 재현 정보와 증거에서 출발하는 진단

버그를 전할 때는 게임 빌드, 활성 모드, 수행한 조작, 기대한 결과, 실제 결과 다섯 가지를 짚어 주세요. 해당 실행 시간대의 로그를 읽어 반복 메시지를 근본 원인별로 묶고, 뒤이은 로드를 막는 파싱·참조 오류부터 치웁니다. 마지막 줄 한 줄이나 지난 실행의 묵은 로그, 단발성 추측에 기대지 말고 실행 흐름 전체를 대조합니다.

파일 간 문제는 정의에서 사용처까지 추적한 뒤 스코프, 상태, 의존성, 에셋을 확인합니다. 확정된 결함, 추정 단서, 설계 취향, 미검증 가설을 분명히 나누어 확인된 원인에만 수정을 집중합니다.

네이티브 디버깅이나 덤프 분석은 문제 해결에 꼭 필요하고 도구와 동의가 갖춰졌을 때만 진행하며 개인 정보는 안전하게 다룹니다. 평범한 `error.log` 점검이 상의 없이 프로세스 연결이나 전체 메모리 수집으로 번지지 않게 선을 지킵니다.

## 10. 위험에 맞는 적정 검증

| 변경 또는 증거 | 알맞은 확인 | 추가로 염두에 둘 부분 |
| --- | --- | --- |
| 짧은 문구·주석·익숙한 템플릿 미세 수정 | diff로 서식과 자리표시자 확인 | 실행 중 게임 로직은 별도 범위 |
| 스크립트·참조·인코딩·에셋 연결 | 변경 파일 정적 검사와 참조 추적 | 게임 내 스코프, 실행 시점, UI 상호작용 |
| 오프라인 모델·웹·이미지 미리보기 | 규칙 계산, 배치, 픽셀, 파일 형식 확인 | 네이티브 입력, 셰이더 렌더링, 세이브 동작 |
| 실기 조작 | 지정한 빌드·플레이세트·시나리오 직접 관찰 | 다른 버전, 기존 세이브, 멀티플레이, 미실행 분기 |

실패 위험에 맞춰 가장 간결하면서 충분한 확인을 고르고, 여전히 유효한 증거는 재사용합니다. 작은 작업은 대개 관련 확인 항목 0~3개면 충분합니다. 게임 실행이 필요할 때는 허가된 범위 안에서 가장 짧은 경로(열려 있는 세션, 테스트 세이브, 새 캠페인)를 택하고 준비와 복구 시간까지 예산에 넣습니다. 수정 뒤에는 바뀐 부분만 표적 재확인합니다.

게임 실행은 정적 검사로 답할 수 없는 의문을 확인하는 데 씁니다. 데스크톱 제어 도구가 없거나 실기 테스트를 원하지 않으면 “실기 미확인”으로 적고 필요한 수동 확인 진입점만 간결히 안내합니다. 새 수정에는 언제나 새 근거를 짝지으세요.

## 11. 문서, Git, 전달

- **문서는 역할에 맞게 간결하게**: 기술 가이드는 현재 유효한 구조·진입점·상태·호환성·빌드 규칙을 담고, 개발 로그는 이번 변경과 검증 근거를 기록합니다. 작은 변경은 기존 문서의 해당 절을 갱신하는 것으로 충분합니다.
- **Git 작업은 단계별로 분명하게**: 커밋 전에 작업 트리와 스테이징 diff를 살펴 다른 작업의 미완성 변경을 지키고, 에셋 이름 변경·생성 스크립트·참조는 한꺼번에 전달합니다. 커밋, 푸시, 릴리스 발행, 창작마당 업로드는 각각 별도 작업이며 요청과 허가에 따라 설정된 원격·브랜치에 실행합니다.
- **투명한 인계와 공개 문서 위생**: 완료 범위, 검증 범위, 미확인 동작, 현재 Git 상태를 깔끔히 보고합니다. 공개 문서에는 범용 예시와 자리표시자 경로만 쓰고 개인 폴더, 특정 프로젝트 캐릭터, 고유 규칙, 확인 불가능한 사적 검수 기록은 넣지 않으며 출처와 라이선스를 바르게 유지합니다.

## 12. 바로 응용하는 요청 템플릿

**구현 가능성만 검토하기**

> 이 모드에서 진행 상태를 저장하는 경영 패널을 만들 수 있는지 검토해 줘. 입력 인터페이스, 상태 소유자, 세이브 로드·일시 정지 동작, 성능 한계, 최소 검증 계획을 정리해 줘. 먼저 분석만 하고 파일 수정이나 게임 실행은 아직 하지 마.

**기존 버그 고치기**

> 이 이벤트를 두 번째로 열면 보상이 또 지급돼. 진입점, 플레이어 문구, 상태 수명을 따라가 원인을 찾고, 기존 세이브 진행을 지키면서 중복 수령을 막아 줘. 관련 분기만 확인하고 다른 보상 수치는 그대로 둬.

**조각난 파일 정리하기**

> 최근 추가된 작은 파일들을 기능별로 통합해 줘. ID, 로드 순서, 호환성 경계를 그대로 유지하고 생성 스크립트와 참조도 함께 갱신해 줘. 플레이 규칙은 바꾸지 말고, 전후 경로 대응표와 내용 동일성 확인 결과를 알려 줘.

**에셋 교체와 다국어 동기화**

> 첨부한 원본으로 이 화면 배경을 교체해 줘. 기존 소비 컨트롤 크기에 비율을 맞춰 조정하고 기존 디자인의 여백 방식을 유지하며 원본은 보존해 줘. 지원하는 모든 언어의 안내 문구를 갱신하고 가장 긴 문장과 새 경로를 확인한 뒤 출력 형식과 점검 결과를 보고해 줘.

**배포 및 푸시 준비**

> 완료된 수정을 릴리스 노트로 정리해 줘. 실기 확인한 내용과 아직 미확인인 부분을 또렷하게 구분하고, 스테이징 범위를 확인한 뒤 설정된 대상 브랜치에 커밋·푸시해 줘. 무관한 로컬 변경은 건드리지 말고 이번에는 릴리스 발행이나 창작마당 업로드는 생략해 줘.
