# HOI4 모드 개발 가이드

[简体中文](hoi4-modding-guide.zh-CN.md) | [English](hoi4-modding-guide.en.md) | [日本語](hoi4-modding-guide.ja.md) | [Русский](hoi4-modding-guide.ru.md) | 한국어

AI와 함께 Hearts of Iron IV 모드를 만드는 제작자와 유지·보수 담당자를 위한 가이드입니다.
원하는 플레이 방식을 일상적인 말로 설명하거나, 수정할 스크립트와 인터페이스, 결함을 직접
지정할 수 있습니다. 역사·대체 역사·인물 중심·게임플레이·대형 개편 모드에 공통으로 적용할 수
있으며, 특정 세계관이나 국가, 제작자의 컴퓨터 경로를 전제로 하지 않습니다.

아래 예시는 AI에게 작업을 요청하는 방법을 보여 줍니다. 실제 동작은 대상 게임 빌드,
의존 모드 조합, 세이브에서 확인해야 합니다. 세 스킬의 기술 참고 자료는 주로 영어로 되어
있으며, 사용자용 가이드는 위에 나열된 언어로 읽을 수 있습니다.

## 1. 시작하기

세 스킬을 함께 설치하고 각 폴더의 상대 경로를 유지하세요.
[설치 및 공유 안내](../../../../docs/INSTALLATION.md)에서 클라이언트별 방법을 확인할 수
있습니다. 작업할 모드를 열고 AI가 프로젝트 지침과 관련 코드를 읽도록 하세요. 작은 변경은
관련 파일부터 보면 됩니다.

| 할 일 | 주로 사용할 스킬 | 기대 결과 |
|---|---|---|
| 아이디어를 새 콘텐츠나 하나의 시스템으로 구현 | `hoi4-content-builder` | 스크립트, 에셋, 문구가 연결되어 플레이어가 진입하고 사용할 수 있는 기능 |
| 스크립트, 현지화, 인터페이스, 호환성 로직 수정 | `hoi4-pdx-modding` | 대상 빌드와 프로젝트 규칙에 맞는 구현 |
| 결함 진단, 성능 검토, 버전 이행 문제 조사 | `hoi4-review-debug` | 근거가 분명한 조사 결과와 합의된 범위의 수정 |

지원되는 클라이언트는 스킬을 자동으로 선택할 수 있고, 사용자가 이름을 직접 지정할 수도
있습니다. 스킬은 작업 절차와 참고 자료를 제공합니다. 파일 접근, 명령 실행, 네트워크, 게임
조작 가능 여부는 클라이언트에 따라 다릅니다. 선택 사항인 로컬 MCP 도구는 설치 파일과 로그
등을 읽어 근거를 제공하며, 게임 실행이나 모드 수정 권한은 없습니다.

첫 요청은 다음처럼 쓸 수 있습니다.

> 현재 모드에 ‘산업 지원’ 결정을 추가해 줘. 플레이어가 정치력 50을 쓰면 30일 동안 생산
> 보너스를 받게 해 줘. 보너스가 적용되는 동안에는 결정을 다시 선택할 수 없고, 효과가 끝나면
> 다시 선택할 수 있어야 해. AI는 전쟁 중에만 이 결정을 고려하게 해 줘. 기존 의존성은 유지하고
> 프로젝트에서 지원하는 모든 언어의 문구를 작성해 줘. 관련 프로젝트 지침과 바닐라 사례를
> 확인한 뒤 구현하고 필요한 정적 검사를 해 줘. 게임 실행과 커밋은 아직 하지 마.

비용과 기간, 사용 조건은 예시입니다. 자신의 설계에 맞게 바꾸고 구체적인 구현 방법은 AI가
프로젝트와 게임 빌드를 확인한 뒤 정하도록 하세요.

## 2. 확인할 수 있는 동작으로 설명하기

간단한 요청이면 몇 문장으로 충분합니다. 규모가 큰 작업에서는 프로젝트에서 확인하기
어려운 정보를 아래 항목 가운데 필요한 만큼 덧붙이세요.

| 항목 | 설명할 내용 |
|---|---|
| 목표 | 새 모드, 기존 기능 변경, 구현 가능성 조사, 읽기 전용 검토 가운데 무엇인지 |
| 환경 | 프로젝트 위치, 대상 게임 빌드, 관련 DLC, 의존 모드, 실제 로드 순서 |
| 플레이어의 이용 흐름 | 진입점, 화면에 보이는 내용, 조작과 결과, 종료 방법 |
| 규칙 | 비용, 조건, 효과, 기간, 실패, 취소, 반복 사용 |
| 상태의 범위 | 어느 국가나 객체가 소유하는지, 창 닫기·세이브 불러오기·캠페인 시작 시의 동작 |
| AI와 호환성 | AI가 사용하는지, 언제 사용하는지, 기존 세이브와 멀티플레이 지원 조건 |
| 에셋과 언어 | 원본, 사용 권한, 시각적 요구 사항, 지원 언어 |
| 작업 범위 | 수정할 수 있는 파일, 게임 테스트 허용 여부, 커밋과 배포 범위 |

“분석만 해 줘”, “이 문제만 고쳐 줘”, “테스트를 더 추가하지 마”처럼 작업 범위를
직접 적으세요. 사용자가 중단을 요청하면 AI는 새 검사나 수정을 시작하지 않고 현재 상태를
알려야 합니다. “지금 하는 것까지만 끝내 줘”에서 현재 작업은 이미 진행 중인 한정된 작업 한
건을 뜻합니다.

## 3. 프로젝트와 근거 확인하기

기존 모드를 다룰 때는 기술 지침, 영향받는 게임 내 문구, 해당 기능을 실제로 호출하는 코드부터
읽습니다. 변수 이름이나 파일명만으로 플레이 방식과 기능의 목적을 판단하기는 어렵습니다.

대상 버전의 바닐라 파일과 설치본에 포함된 문서, 스킬의 템플릿과 키트, 실제로 활성화된
의존 모드에서 문법과 연결 방식을 확인합니다. 템플릿과 현재 사용처가 어긋나면 현재 사용처를
기준으로 템플릿을 고칩니다. 위키와 커뮤니티 자료는 조사에 활용하고, 오래된 예제는 대상
빌드에서 확인된 동작과 대조합니다.

관련 `descriptor.mod` 설정, `replace_path`, 로드 순서와 겹치는 정의를 확인합니다.
호환성 패치를 만들려면 정확한 의존 모드 버전과 그 모드가 실제로 쓰는 식별자가 필요합니다.
설치 파일이나 게임 실행에서 얻은 증거가 부족하면 확인하지 못한 부분을 명시합니다.

## 4. 진입점부터 결과까지 연결하기

진입부터 결과까지 작동하는 가장 작은 단위의 기능을 먼저 만들고, 그다음 콘텐츠를 확장합니다.
결정이라면 다음과 같은 흐름을 확인할 수 있습니다.

```text
분류와 결정 항목 → 표시·선택 조건 → 비용과 효과 → 상태·수정치 → 결과 안내
                    함께 연결할 요소: 현지화, 아이콘, AI 사용 규칙
```

이벤트, 국가중점, 기술, 장비, 군수 산업체(MIO), 인물, GUI, 음악에는 각각 다른 사용처와
리소스 연결이 필요합니다. 진입점, 아이콘, 문구, 실제 효과까지 연결해야 플레이어가 기능을
사용할 수 있습니다.

기존 동작을 바꿀 때는 실제 호출 경로를 따라가며 `ROOT`, `FROM`, 국가, 주, 인물 등의
스코프를 확인합니다. 효과마다 어느 객체의 상태를 읽거나 바꾸는지 확인하세요. 호출 대상이
없을 수 있거나 세이브에서 별도 처리가 필요한 경우 방어 조건을 추가합니다. 문제가 있어도
조용히 기본값을 반환하면 끊어진 연결을 놓칠 수 있습니다.

복잡한 시스템은 오프라인 규칙 모델과 작은 게임 내 예제로 시작할 수 있습니다. 예제에도
설계의 핵심 동작이 들어 있어야 합니다. 객체 여러 개를 다루는 기능이라면 생성, 조회, 삭제,
빈 슬롯 재사용을 모델링하세요. 고정된 객체 하나만으로 전체 설계를 확인하기는 어렵습니다.
가능성만 조사해 달라는 요청에는 제약, 구현 선택지, 확인 방법을 제시하고 구현 지시를 기다립니다.

## 5. 상태, 세이브, 시간 설계하기

세이브에 남는 변수, 플래그, 배열, 이벤트 대상에는 각각 소유자, 목적, 유지 기간이 필요합니다.
자료 구조를 고르기 전에 아래 질문에 답해 보세요.

- 언제 초기화하나요? 기존 세이브에서도 새 콘텐츠를 초기화할 수 있나요? 초기화가 두 번 실행되면 보상을 또 받나요?
- 창을 다시 열면 진행이 이어지나요, 초기화되나요, 아니면 표시만 갱신되나요? 실패, 취소, 재시작은 별도 경로인가요?
- 세이브를 불러오거나, 조작할 국가를 바꾸거나, 멀티플레이 호스트 연결이 끊겼을 때 어떤 상태가 남나요? 여러 플레이어가 공유하는 상태와 각자 소유하는 상태는 무엇인가요?
- 무엇을 ‘첫 완료’로 보나요? ‘각 세이브에서 게임마다, 난이도마다 한 번’이라면 전역 플래그 하나로는 부족하고 게임과 난이도별 기록이 필요합니다.

세이브에 저장되는 식별자와 기존 상태를 유지합니다. 이름이나 의미를 바꾸려면 기존 값을
옮기는 방법을 설계하세요. 파일명을 바꾸는 것만으로는 보통 세이브 속 식별자가 바뀌지 않습니다.

애니메이션 시간과 게임 규칙에 쓰는 시간을 구분합니다. 게임의 일수와 시간, 클릭,
명시적으로 진행되는 로직 단계는 각각 다르게 동작합니다. 일시 정지와 게임 속도의 영향을
고려하세요. 복잡도에 맞춰 상태 머신, 이벤트에 따른 갱신, 처리량을 제한한 일괄 처리를
사용합니다. 일반적인 기능에는 범용 인터프리터까지 필요한 경우가 드뭅니다.

## 6. GUI, 시각 효과, 에셋

배치, 클릭 영역, 갱신 조건, 창을 닫을 때의 동작, 규칙의 결과를 보여 주는 방식을 함께
정합니다. 긴 문구, 대상 해상도, 화면 배율, 가림과 레이어 순서, 창을 다시 열었을 때의 동작을
확인하세요.

셰이더가 스크립트 상태나 정확한 마우스 위치, 창을 열 때마다 초기화되는 타이머를 자동으로
받는다고 가정하지 마세요. 기울어진 그림과 클릭 영역, 장식용 지구본과 조작 가능한 지도,
반복 애니메이션과 한 번만 재생하는 연출은 각각의 동작을 확인합니다. 브라우저 미리보기나
셰이더 단독 컴파일만으로는 게임에서의 파싱과 조작을 확인할 수 없습니다.

미디어는 원본에서 가공하고 출처와 사용 권한을 기록합니다. 실제 사용처를 기준으로 크기,
형식, 알파, 밉맵, 잘라낼 영역과 여백을 확인하세요. 한 이미지의 설정을 다른 이미지에 그대로
적용할 필요는 없습니다. 손실 압축으로 DDS를 다시 만들면 선화가 손상될 수 있습니다. 파일
용량과 화질, GPU 메모리 사용량은 별도로 확인합니다.

프레임 애니메이션은 프레임 수, 재생 속도, 반복 여부, 아틀라스 배치를 지정합니다. 큰
이미지에는 텍스처 크기 제한과 메모리 사용량을 고려하세요. 음악은 메인 메뉴와 게임 내
음악 플레이어에 각각 어떻게 등록되는지, 지원 형식과 재생 조건이 무엇인지 구분합니다. 에셋의
이름이나 번호를 바꿀 때는 명시적 참조와 엔진의 이름 규칙을 확인하고 관련 없는 에셋은
그대로 둡니다.

원본, 추출한 프레임, 미리보기, 임시 변환 파일은 프로젝트에서 정한 에셋 또는 빌드 위치에
보관합니다. 배포 패키지에는 실행에 필요한 파일을 담고, 중간 산출물은 필요에 따라 관리합니다.

## 7. 기능과 함께 현지화 설계하기

지원하는 모든 언어가 같은 기능과 키를 다루도록 합니다. 번역 전에 용어, 고유명사, 플레이
개념을 정리합니다. 식별자, 변수, 아이콘 표기, 색상 코드, 실행 중 값이 채워지는 자리표시자를
유지합니다. 제작자에게만 필요한 설명은 게임 내 문구와 분리하세요.

프로젝트 규칙과 템플릿을 기준으로 파일명, 언어 헤더, 인코딩, 들여쓰기, 키 문법을 확인합니다.
한국어는 `localisation/korean/` 아래에 `_l_korean.yml` 접미사를 붙인 파일을 두고
첫 줄에 `l_korean:`을 씁니다. 파일은 BOM이 있는 UTF-8로 저장합니다.
[기본 한국어 템플릿](../../../hoi4-content-builder/assets/templates/localisation_l_korean.yml)과
[동적 값이 들어간 한국어 템플릿](../../../hoi4-content-builder/assets/templates/localisation-advanced/localisation_advanced_l_korean.yml)을
참고할 수 있습니다. 이름, 설명, 자동 생성되는 수정치 설명, 사용자 정의 툴팁은 서로 다른
경로로 표시될 수 있으므로 각 문구의 실제 사용처를 확인합니다.

새로 추가하거나 바꾼 긴 문구는 줄바꿈, 버튼 너비, 글리프 표시를 확인합니다. 사용자 정의
비트맵 글꼴을 쓴다면 실제 화면에 적용되는 글꼴에 한글과 필요한 문장 부호가 있는지 살펴보세요.
번역본마다 비용, 조건, 실패, 보상이 같은 뜻으로 전달되어야 합니다. 언어 선택 링크와 사용자
가이드, 공개 소개도 함께 갱신해 제목만 번역되거나 옛 안내가 남는 일이 없도록 합니다.

## 8. 성능과 파일 정리

최적화 방법을 고르기 전에 실제 비용부터 찾습니다. 자주 실행되는 `on_actions`, 전체 순회,
중첩 반복, 표시 조건의 반복 평가, 대형 애니메이션 텍스처를 확인하세요. 결과가 상태 변경
때에만 달라진다면 이벤트 기반 갱신이나 캐싱을 고려할 수 있습니다. 캐시를 언제 갱신하거나
폐기할지도 정합니다.

실행 횟수를 줄인다는 이유로 매일 적용되는 규칙을 매주 적용되도록 임의로 바꾸지 마세요.
나누어 처리할 때는 진행 위치와 한 번에 처리할 양을 정하고, 설계한 결과와 플레이어에게
보이는 피드백을 유지합니다.

파서가 읽는 폴더, 로드 규칙, 상태의 수명이 같은 파일 조각은 담당 기능 단위로 묶습니다.
로드 순서, 호환성, 생성 도구의 관리 범위, 유지·보수상의 이유로 나눈 파일은 분리해 둡니다.
파일 수를 줄이면 주로 관리와 시작 시 파일 접근에 도움이 됩니다. 실행 중 FPS가 향상됐는지는
별도 측정이 필요합니다.

병합할 때는 정의, 네임스페이스, 순서, 중복 키, 리소스 참조를 비교합니다. 같은 키에 서로
다른 값이 있다면 어떤 값이 설계에 맞는지 판단하세요. 다음 빌드가 옛 경로를 다시 생성하지
않도록 생성 도구를 갱신합니다. 결과물을 재현할 수 있어야 하며, 수동 수정은 기준이 되는
원본에도 반영합니다.

## 9. 재현 절차와 근거를 바탕으로 진단하기

게임 빌드, 활성 모드, 수행한 조작, 기대한 결과, 실제 결과를 기록합니다. 해당 시간대의
로그를 읽고 반복 메시지를 원인별로 묶습니다. 이후 콘텐츠 로드를 막을 수 있는 파싱 오류와
참조 오류를 먼저 확인하세요. 마지막 로그 줄, 종료 후 남아 있던 이전 로그, 추측 하나만으로
충돌 원인을 확정하기는 어렵습니다.

여러 파일에 걸친 문제는 정의와 사용처를 연결해 보고 스코프, 상태, 의존성, 에셋을 확인합니다.
확인된 결함, 정황상 유력한 원인, 설계 선호, 아직 검증하지 않은 가설을 구분합니다. 수정은
확인한 원인에 집중합니다.

문제 해결에 필요하고 도구와 권한이 갖춰졌다면 네이티브 디버깅이나 덤프 분석을 활용합니다.
개인 정보는 보호합니다. 일반 로그 조사만으로 충분한 단계에서는 프로세스 연결, 도구 설치,
전체 메모리 수집으로 곧바로 확대하지 않습니다.

## 10. 필요한 만큼 검증하기

| 변경 또는 증거 | 적절한 확인 | 확인 범위 밖의 예 |
|---|---|---|
| 짧은 문구, 주석, 익숙한 템플릿 수정 | diff에서 서식과 자리표시자 확인 | 전체 플레이 검증 |
| 스크립트, 참조, 인코딩, 에셋 연결 | 영향받은 파일의 정적 검사와 참조 추적 | 게임 내 스코프, 실행 시점, 인터페이스 동작 |
| 오프라인 모델, 웹 또는 이미지 미리보기 | 규칙, 레이아웃, 픽셀, 미디어 형식 확인 | 게임 내 입력, 렌더링, 세이브 동작 |
| 게임 내 조작 | 지정한 빌드·플레이세트·시나리오에서 관찰 | 다른 버전, 세이브, 멀티플레이, 모든 분기 |

실패할 가능성이 있는 부분을 확인할 수 있는 가장 작은 검사를 고르고, 아직 유효한 증거는
재사용합니다. 작은 작업이라면 관련 확인 항목은 보통 0~3개입니다. 게임 확인이 필요하면
현재 세션, 테스트 세이브, 새 캠페인 가운데 허용된 가장 짧은 경로를 택하고, 준비와 정리도
시간에 포함합니다. 수정 후에는 필요한 항목만 다시 확인합니다.

게임 실행은 정적 검사에서 답을 얻을 수 없는 질문을 확인하는 데 씁니다. 게임을 조작할 수
없거나 사용자가 테스트를 원하지 않으면 게임 내 동작은 미확인으로 기록하고, 필요한 경우
수동 확인에 쓸 진입점을 알려 줍니다. 예전 테스트 기록은 변경된 동작을 다시 확인한 근거가
될 수 없습니다.

## 11. 문서, Git, 전달

기술 가이드에는 현재 구조, 진입점, 상태, 호환성, 빌드 규칙을 기록합니다. 개발 로그에는
변경과 근거를 남깁니다. 작은 수정은 기존 문서를 갱신하는 것으로 충분한 경우가 많습니다.

커밋 전에 작업 트리와 스테이징된 diff를 확인하고 다른 기여자가 진행 중인 변경을 보존합니다.
에셋 이름 변경, 생성 도구, 참조는 함께 반영합니다. 커밋, 푸시, 릴리스 생성, 창작마당
업로드는 각각 별도 작업입니다. 사용자 요청과 이미 받은 권한에 맞춰 프로젝트에 설정된
원격 저장소와 브랜치를 사용합니다.

완료한 범위, 확인한 부분, 아직 확인하지 못한 동작, Git 상태를 전달합니다. 공개 문서에는
다른 프로젝트에도 적용할 수 있는 예시와 경로 자리표시자를 씁니다. 비공개 경로, 특정
프로젝트의 인물이나 고유 규칙, 확인할 수 없는 개인별 검수 결과는 공개 예시에서 제외합니다.
출처와 라이선스는 정해진 문서에 기록합니다.

## 12. 그대로 응용할 수 있는 요청 예시

**구현 가능성만 조사하기**

> 이 모드에서 진행 상태가 저장되는 관리 패널을 만들 수 있는지 검토해 줘. 입력 방식,
> 상태의 소유자, 불러오기와 일시 정지 시의 동작, 성능 한계, 최소 확인 절차를 알려 줘.
> 아직 파일을 수정하거나 게임을 실행하지 마.

**기존 동작 수정하기**

> 이 이벤트를 두 번째로 열면 보상을 또 받아. 진입점, 플레이어가 보는 문구, 상태의 수명을
> 추적해 줘. 기존 세이브의 진행을 유지하면서 중복 수령을 막아 줘. 관련 분기만 확인하고
> 다른 보상 수치는 그대로 둬.

**파일 합치기**

> 최근 추가한 파일 조각을 기능별로 정리해 줘. 식별자, 로드 순서, 호환성 범위를 유지하고
> 생성 도구와 참조도 갱신해 줘. 게임 규칙을 바꾸지 말고, 이전 경로와 새 경로의 대응표와
> 내용이 동일한지 확인한 결과를 알려 줘.

**미디어 교체와 번역**

> 이 인터페이스의 배경을 첨부한 원본으로 바꿔 줘. 기존 사용처의 크기에 맞추되 비율을
> 유지하고, 디자인에 맞춰 여백을 넣어 줘. 원본은 보관해 줘. 지원하는 모든 언어의 안내
> 문구를 갱신하고, 가장 긴 문구와 새 에셋 경로를 확인해 줘. 결과물의 형식과 확인 결과를
> 알려 줘.

**배포 준비**

> 끝난 수정 내용을 릴리스 노트로 정리해 줘. 테스트한 동작과 아직 확인하지 않은 부분을
> 구분해 줘. 스테이징 범위를 확인한 뒤 관련 변경만 커밋해서 프로젝트에 설정된 대상
> 브랜치에 푸시해 줘. 이번 작업에서는 릴리스 발행이나 창작마당 업로드는 하지 마.
