# HOI4 通用 Mod 开发指南

简体中文 | [English](hoi4-modding-guide.en.md) | [日本語](hoi4-modding-guide.ja.md) | [Русский](hoi4-modding-guide.ru.md) | [한국어](hoi4-modding-guide.ko.md)

这份指南面向使用 AI 开发《钢铁雄心 IV》Mod 的作者和维护者。你可以用自然语言说明玩法，也可以直接指定脚本、接口或故障。它适用于历史、架空、角色、玩法扩展和大型整合类 Mod，不依赖某个作品、国家或作者的电脑目录。

下文总结可复用的开发方法。示例用于表达需求，不代表已经在你的游戏版本、依赖组合或存档中验收。三个 skills 的内部技术资料仍以英文为主；本使用指南提供五种完整语言版本。

## 1. 从哪里开始

将三个 skills 一起安装，保持它们的相对目录。客户端安装方式见[安装与共享说明](../../../../docs/INSTALLATION.md)。先打开目标 Mod 工程，让 AI 阅读仓库说明和相关代码；不需要为一次小改动扫描整份工程。

| 任务 | 主要使用的 skill | 应得到的结果 |
|---|---|---|
| 从想法制作新内容或完整系统 | `hoi4-content-builder` | 可进入、可操作、具备脚本、素材和文本的功能 |
| 修改脚本、本地化、界面或兼容逻辑 | `hoi4-pdx-modding` | 与目标版本和现有工程一致的实现 |
| 查错、审查、性能或版本迁移诊断 | `hoi4-review-debug` | 有证据的问题定位及约定范围内的修复 |

支持自动匹配的客户端可以自行选择 skill，也可以显式指定名称。Skills 提供工作方法和参考资料；读写文件、运行命令、访问网络或控制游戏的能力取决于当前客户端。可选的本地 MCP 工具只提供只读证据，不会替你启动游戏或写入 Mod。

第一次可以这样说：

> 请在当前 Mod 中增加一个“工业援助”决议。玩家支付 50 政治点，获得持续 30 天的生产加成；生效期间不能重复购买，到期可再次使用。AI 只在战争期间考虑使用。保留现有依赖，补齐项目已支持的语言。先读取相关工程说明和原版示例，完成实现和必要静态检查，暂不启动游戏或提交。

数值和限制只是示例。将它们换成你的设计即可；AI 应自行查明适用的实现方式。

## 2. 把想法说成可验收的行为

一个简短请求通常足够。较复杂的任务可以补充下列信息，已能从工程中读到的内容无需重复填写。

| 信息 | 需要明确的内容 |
|---|---|
| 目标 | 新建 Mod、修改现有功能、只做可行性分析，还是只读审查 |
| 环境 | 工程位置、目标游戏版本、相关 DLC、依赖及实际加载顺序 |
| 玩家路径 | 从哪里进入、看到什么、操作后发生什么、如何退出 |
| 规则 | 成本、条件、效果、持续时间、失败、取消和重复操作 |
| 状态范围 | 属于哪个国家或对象；关闭窗口、读档、新开局后如何处理 |
| AI 与兼容性 | AI 是否使用、何时使用；是否需要旧存档或多人兼容 |
| 素材与语言 | 可使用的原件、授权范围、画面要求及支持语言 |
| 工作边界 | 可修改范围、是否允许运行游戏、是否提交或发布 |

把“先分析，别实施”“只修这个问题”“不要再追加测试”等要求直接写出来。要求停止时，AI 应停止启动新的检查和修复，并说明当前完成状态；“做完当前就停”指正在进行的一个有界步骤。

## 3. 先确认工程和证据来源

现有项目先读技术说明、相关玩家文本和调用者。变量名不能代替玩法说明，文件名也不能证明内容的实际用途。

语法与接口按目标安装核验：当前原版文件及随游戏提供的文档、技能模板与套件、实际启用的依赖。模板与当前消费者冲突时，应按当前证据修正。Wiki 和社区资料可以提供线索，但不能让旧范例覆盖实际版本行为。

检查与当前改动有关的 `descriptor.mod`、`replace_path`、加载顺序和同名定义。兼容补丁要对照确切的依赖版本，避免猜测依赖中的 ID。如果缺少安装文件或运行证据，应写清楚尚未确认的部分。

## 4. 做通一条完整功能链

先实现能够完整走通的最小功能，再扩展内容量。一个决议的完整链路可能是：

```text
分类与入口 → 显示/可用条件 → 成本与效果 → 状态或修正 → 玩家反馈
                       ↘ 本地化、图标、AI 使用规则
```

事件、国策、科技、装备、MIO、角色、GUI 和音乐也各自有消费者与资源链。不能只生成定义文件而遗漏入口、图标、文本或实际效果。

修改既有功能时，沿真实调用链确认 `ROOT`、`FROM`、国家、州、角色等 scope，明确效果从谁身上读取或写入状态。只在调用者确实可能缺失、或保存生命周期确有需要时增加保护逻辑，避免用静默回退掩盖接线错误。

复杂系统可以先做离线规则模型和小规模原生样例，但样例必须保留设计所需的关键机制。例如，需要多个实体的系统，应在模型中考虑创建、查找、删除和槽位复用；一个硬编码对象不足以证明完整方案。只有可行性请求时，应交付限制、可选方案和验证路径，等待实施指令。

## 5. 把状态、存档和时间设计清楚

每个长期变量、flag、数组或事件目标都应有归属、用途和生命周期。先回答这些实际问题，再选择数据结构：

- 初始化何时发生？新增内容能否在旧存档中初始化？重复初始化会不会重发奖励？
- 关闭再打开窗口是继续、重置还是只刷新显示？失败、取消和重开是否走不同路径？
- 读档、切换国家、宿主消失时，哪些状态仍有效？多人共享和各玩家独立的状态如何区分？
- “首次完成”按什么范围记录？例如“每个存档内，每种玩法的每个难度各一次”需要分别记录玩法与难度，不能共用一个全局首次标记。

持久化 ID 和既有存档状态需要保留，改名或改变含义时要有迁移设计。更换文件名通常不等于迁移存档中的标识符。

把界面动画时间与玩法时间分开。日、小时、点击或显式逻辑步进各有不同语义；暂停和游戏速度也要纳入设计。用状态机、事件驱动更新或有限批次处理来表达确实需要的复杂度，不要为普通功能先造通用解释器。

## 6. GUI、视觉效果与素材

界面需求应同时说明布局、点击区域、刷新条件、关闭路径和规则反馈。重点观察最长文本、目标分辨率、缩放、遮挡、层级与关闭后重开行为。

着色器负责画面时，不应假设它自动拥有脚本状态、精确鼠标位置或每次打开重置的时钟。倾斜卡片的外观与点击框、装饰性地球与可操作主地图、循环动画与一次性演出，都需要分别核验相关接口。浏览器预览和独立着色器编译不能证明游戏中的解析与交互正常。

素材处理从原件开始，保留来源与使用授权。按实际消费者确认尺寸、格式、alpha、mipmap、裁切或补边方式，不把某张图的参数套用给所有资源。DDS 有损重编码可能损伤线条；文件更小并不等于画质或显存占用更合适。

帧动画要明确帧数、播放速度、循环和图集布局；大图要考虑纹理尺寸与显存。音乐要区分主菜单和游戏内播放器的注册、格式与触发方式。修改路径或编号时，同步查找显式引用及引擎命名约定，并保留其余资源的内容。

原件、提取帧、预览和临时转换文件放在项目约定的素材或构建位置。发布包只保留运行所需内容；不要把保存原件误解为必须将所有中间文件提交到仓库。

## 7. 多语言从功能设计阶段开始

所有支持语言应覆盖相同的功能和本地化键。先统一术语、人物称谓及游戏概念，再翻译；ID、变量、图标标记、颜色代码和动态占位符保持一致。不要把开发指令放进玩家文案。

核对语言文件名、语言头、编码和缩进，并遵循项目及技能模板的键格式。文本存在于文件中，不代表目标界面会使用它：名称、说明、自动生成的 modifier 文本和自定义 tooltip 的消费方式可能不同。

对新增或变动的长文本检查换行、按钮宽度和字体显示。翻译需要说明同样的成本、条件、失败与奖励；语言切换入口、使用指南和公开说明也应同步更新，避免某种语言只有标题或过时内容。

## 8. 性能优化与文件整合

先找实际开销，再选择优化。关注高频 `on_actions`、全局遍历、深层循环、反复计算的显示条件和大面积动态纹理。能在状态变化时更新的结果，可考虑事件驱动或缓存，但必须明确缓存失效时机。

不要为了降低执行频率而悄悄把每日机制改成每周机制。分批处理需要记录进度并设定上限；玩法结果与可见反馈仍应符合原设计。

按功能归属整合相同解析目录、加载规则和生命周期的碎片文件。保留确有加载顺序、兼容性、生成器或维护边界的拆分。减少文件数量主要改善维护与启动文件读取，不能据此承诺持续帧率提升。

合并时核对定义、命名空间、顺序、重复键和资源引用。相同键但不同值需要判断语义。已有生成器必须同步修改，避免下次构建重新生成旧路径；生成输出应可重复，手工修改应回到对应源文件。

## 9. 排错从复现和证据开始

说明“哪个版本、哪些 Mod、执行什么操作、预期与实际分别是什么”。读取对应时段的日志，按根因合并重复信息，优先处理会阻断后续内容的解析或引用错误。最后一条日志、退出后的旧日志和单次猜测都不足以确定崩溃根因。

跨文件问题沿定义和消费者追踪，再检查 scope、状态、依赖与资源。确定性缺陷、启发式线索、玩法偏好和未验证假设应分别说明，修复范围围绕已发现的原因。

原生调试或转储分析只在问题需要、工具可用且授权覆盖时开展，并处理隐私数据。普通日志排查不应自动升级为进程附加、工具安装或完整内存采集。

## 10. 用足够的证据验收

| 改动或证据 | 合适的检查 | 不能据此声称什么 |
|---|---|---|
| 文字、注释、已知模板的小改动 | 阅读 diff，保留既有格式和占位符 | 所有玩法都已测试 |
| 脚本、引用、编码或资源接线 | 受影响文件的静态校验与引用核对 | scope、时序或界面在游戏内必然正确 |
| 离线模型、网页或图片预览 | 规则计算、布局、像素或资源格式检查 | 原生输入、渲染或存档行为已通过 |
| 实机操作 | 指定版本、播放集和场景的实际观察 | 其他版本、存档、多人和所有分支都已通过 |

按失败风险选择最小充分检查，复用仍适用的证据。小任务通常只需 0–3 个相关观察点；确需实机时，在授权范围内选择最短的当前会话、测试存档或新局路径，预算包含准备与收尾。修复后只做必要定向复验，不机械重跑整套检查。

游戏启动应回答静态检查解决不了的问题。缺少原生操作能力或用户不希望测试时，明确写“实机未验证”，提供必要的手测入口即可。不要声称旧测试记录证明了新改动。

## 11. 文档、Git 与交付

技术说明记录当前有效的结构、入口、状态、兼容和构建约定；开发日志记录本次变化及证据。小改动不需要新增一套文档，更新现有对应位置即可。

提交前查看工作区和暂存 diff，保留其他人的未完成修改。资源更名、生成器和引用一起交付。提交、推送、创建 release 和上传 Workshop 是不同动作，按用户要求及已有授权执行，使用实际配置的远端和分支。

交付时说明完成内容、验证范围、未确认行为和 Git 状态。公共文档使用通用例子和占位路径，不夹带私人目录、项目角色、专用规则或无法复查的个别验收记录。来源与许可证应在适当位置保留。

## 12. 可直接改写的请求

**只评估方案**

> 评估在当前 Mod 中制作可保存进度的经营面板是否可行。说明输入接口、状态归属、读档与暂停行为、性能限制和最小验证方案。先不修改文件或启动游戏。

**修复既有功能**

> 这个事件在第二次打开时重复发放奖励。请从入口、玩家文本和状态生命周期追踪原因，修复重复领取并保留旧存档进度。只验证相关分支，不改其他奖励数值。

**整合文件**

> 将最近增加的碎片文件按功能整合，保留 ID、加载顺序和兼容边界，同步生成器与引用。给出前后路径映射和必要的内容等价核对，不改变玩法。

**替换素材与翻译**

> 用指定原图替换这个界面背景，按现有消费者尺寸等比适配，补边方式沿用设计，保留原件。同步所有支持语言的说明，检查最长文本及新增资源路径。完成后说明格式和检查结果。

**准备交付**

> 将本次已完成的修复整理成更新说明，区分实测与未验证内容。检查暂存范围后提交并推送到当前项目配置的目标分支，保留无关本地改动；本次不发布 release 或 Workshop。
