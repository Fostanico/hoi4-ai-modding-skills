# HOI4 通用 Mod 开发指南

简体中文 | [English](hoi4-modding-guide.en.md) | [日本語](hoi4-modding-guide.ja.md) | [Русский](hoi4-modding-guide.ru.md) | [한국어](hoi4-modding-guide.ko.md)

这是一份写给《钢铁雄心 IV》Mod 作者与维护者的 AI 协作手册。你可以直接用日常语言描述脑海里的玩法，也可以指名道姓地交代脚本、界面或故障。无论你的项目是史实扩展、架空剧本、角色养成还是大型全盘魔改，这套方法都能开箱套用，无需绑定特定题材或个人目录。

下文聚焦通用的工程习惯与协作节奏；文中的示例供你套用需求写法，落地到自己的游戏版本、依赖组合与存档时，仍按目标环境实测为准。三套 Skills 的内部技术手册以英文为主，本用户指南则完整提供五种语言版本。

## 1. 起步：先搭好工作台

把三套 Skills 原样成套安装，保留各自的相对目录结构；各客户端安装步骤见 [安装与共享指南](../../../../docs/INSTALLATION.md)。开工时先打开目标 Mod 工程，让 AI 读一遍项目说明和直接相关的源码——小改动从受影响的文件切入即可，不必动辄全仓通读。

| 你想做的事 | 主力 Skill | 预期交付 |
| --- | --- | --- |
| 把新点子做成完整玩法或系统 | `hoi4-content-builder` | 有入口、能操作，脚本、素材与文案成套就位的功能 |
| 调整脚本、本地化、界面或兼容分支 | `hoi4-pdx-modding` | 贴合目标游戏版本与既有架构的干净改动 |
| 排错、体检、性能优化或版本迁移 | `hoi4-review-debug` | 证据链清晰的根因定位，以及约定范围内的精准修复 |

支持自动匹配的客户端会根据你的描述自行选中 Skill，想走固定流程时直接点名即可。Skills 提供的是方法论与参考依据；读写文件、执行命令、联网或操控游戏窗口的能力由客户端和所挂 MCP 决定——只读的 `hoi4_local` 负责本机取证，按需启用的 `hoi4_desktop` 可在经你授权后协助实机验收。

第一次合作，不妨这样起头：

> 请在当前 Mod 里新增一个“工业援助”决议：玩家花费 50 政治点，换取 30 天的生产加成；效果持续期间不可重复点击，到期后恢复可用；AI 仅在战时考虑启用。保留现有依赖，补齐项目已支持的所有语言。先读相关工程说明和原版写法，完成实现并做必要的静态校验；暂时不用启动游戏，也先别提交。

里面的数值和限制都可以随你的设计替换，具体的 PDX 写法交给 AI 对照本机版本去查。

## 2. 把想法说成能验收的行为

简单需求三两句话就够了；遇到复杂系统，把工程里读不到的关键决策补齐，能省下大量返工：

| 维度 | 建议交代清楚的内容 |
| --- | --- |
| 目标 | 新建 Mod、改动既有功能、只做可行性评估，还是只读体检 |
| 环境 | 工程路径、目标游戏版本、涉及 DLC、依赖 Mod 及真实加载顺序 |
| 玩家路径 | 从哪里点进来、看到什么、操作后发生什么、怎么退出 |
| 规则细节 | 成本、触发条件、效果、持续时间，以及失败、取消、重复触发如何处理 |
| 状态归属 | 归属于哪个国家或对象；关闭窗口、读档、新开局后如何延续或重置 |
| AI 与兼容 | AI 何时使用；是否需要兼容旧存档或联机 |
| 素材与语言 | 原图位置、使用授权、画面构图要求与目标语种 |
| 协作边界 | 允许改哪些文件、能否启动游戏实测、是否提交或发布 |

边界越直白越好：“先分析，先别改代码”“只修这一个 Bug”“做到这里就别加新测试了”。你一旦喊停，AI 会立刻停止启动新检查和新修复，如实交接当前进度；如果你说“做完当前就停”，AI 只收尾正在进行的这一个有界动作，绝不顺手加戏。

## 3. 先认清工程，再核对实证

改旧代码之前，先读项目技术文档、玩家实际看到的文案和真实调用链——想摸清一段逻辑到底在干什么，看消费方和玩家文本远比猜变量名、文件名靠谱。

语法与接口一律向你的目标安装对齐：先看当前版本的原版文件与随游戏生成的文档，再对照技能模板、套件和实际启用的依赖 Mod。如果模板与当前原版消费者打了架，以当前原版为准并顺手修正模板。Wiki 与社区帖子适合找方向，落地前要回到本机当前版本复核。

顺手核对与本次改动相关的 `descriptor.mod`、`replace_path`、加载顺序和同名覆盖。写兼容补丁时对照确切的依赖版本与真实 ID，绝不凭印象盲猜；本地缺少安装文件或实机环境时，直接把尚未确认的边界写清楚。

## 4. 先跑通一条完整闭环

做新功能时，先打通从入口到结果的最小闭环，再往里填内容量。以一个决议为例，完整链路长这样：

```text
分类与入口 → 显示与可用条件 → 成本与效果 → 状态或修正 → 玩家反馈
                       ↘ 本地化、图标与 AI 权重
```

事件、国策、科技、装备、MIO、人物、GUI 与音乐各有各的注册和消费链。光写完定义文件只算半成品，把入口、图标、多语言和实际效果一并接上，才算真正交付。

修改既有功能时，沿着真实调用链逐层核对 `ROOT`、`FROM`、国家、州和角色作用域，弄清每条效果究竟在读写谁的状态。只在调用者确实可能缺席或旧存档迁移需要时加保护条件——与其用静默兜底把接线错误藏起来，不如让契约干干净净、一眼见底。

遇到复杂系统，可以先写离线规则模型或小规模原生原型，但原型里要保留设计真正依赖的核心机制：比如多实体系统就要把创建、查找、删除和槽位复用都演练到位，单靠一个写死的特例撑不起全局架构。如果只让你评估可行性，就交付清晰的能力边界、备选方案和验证路径，等确认后再动手写代码。

## 5. 把状态、存档与时间理顺

每个长期存活的变量、flag、数组或事件目标，都要在落笔前定好归属、用途和寿命。挑数据结构前，先过一遍这四个问题：

- **初始化**：什么时候初始化？旧存档加载新版本时能否安全补齐？重复触发会不会白送第二次奖励？
- **重入与分支**：关掉再打开界面，是续上进度、重新开始，还是只刷新显示？失败、取消与重开是否走独立分支？
- **持久化与联机**：读档、切国或宿主消失后，哪些状态继续有效？联机局里哪些数据全员共享，哪些归各玩家私有？
- **“首次”的粒度**：比如“每个存档里，每种玩法的每个难度各领一次”，就要按玩法和难度分别记账，别图省事塞进同一个全局首次标记。

既有存档依赖的持久化 ID 务必保持稳定；真要改名或改变语义，必须配套迁移方案——引擎存档认的是脚本里的 ID，光改文件名可动不了存档里的数据。

把界面动画时钟和游戏玩法时钟拆开思考：游戏日、小时、玩家点击与显式步进各有语义，暂停和倍速都会影响体验。按实际复杂度选用状态机、事件驱动更新或限额分批处理，常规功能用最直白的脚本表达，不必先搭一套重型通用解释器。

## 6. GUI、着色器与美术音频

提界面需求时，把布局、点击热区、刷新时机、关闭路径和规则反馈打包说清；验收时重点盯住最长译文、目标分辨率、UI 缩放、遮挡层级以及关闭重开后的状态。

写 GUI 着色器时，先查清引擎实际传给它的 uniform 与输入，再设计效果——脚本状态、精确光标坐标或每次开窗归零的计时器都要逐一核实接口。倾斜卡片的视觉轮廓与点击框、装饰地球与可交互大地图、无缝循环动画与一次性演出各有门道；浏览器预览和离线编译用来快速调视觉与语法，最终的解析与交互表现要进游戏眼见为实。

处理美术与音频一律从原件出发，保留出处与授权。尺寸、像素格式、Alpha 通道、mipmap、裁切与补边都按实际消费控件定标准，别拿一张图的参数硬套全库。DDS 反复有损重压会啃坏线条；选格式要兼顾画质、显存与消费端约束，别一味追求最小体积。

做帧动画要明确帧数、帧率、循环方式与图集排布，大图要顾及显存和纹理尺寸上限；配音乐要分清主菜单与局内播放器的注册表、音频格式和触发条件。改名或重编号时，同时搜全显式引用和引擎命名约定，不动无关资源。

原件、拆帧图、预览图和临时转换产物归置在项目约定的构建目录；最终发布包只带运行时必需品，保留原件和把所有中间产物塞进 Git 是两码事。

## 7. 多语言从设计第一天同步推进

所有支持语言保持同一套功能覆盖与本地化键。动笔翻译前先敲定专有名词、人名读音和核心玩法术语，严格保留代码里的 ID、变量、图标标记、颜色代码和动态占位符，别把开发备注漏进玩家文本。

按项目约定与技能模板核对文件名、语言头、编码（UTF-8 BOM）与缩进。文本写进 `.yml` 后，还要顺着消费链路核实目标界面真正读了哪个键——名称、描述、自动拼接的修正文本和自定义 tooltip 常常各走各的规则。

新增或改长的句子要检查换行、按钮宽度与字库缺字；各语种对成本、条件、失败与奖励的表述必须语义一致。别忘了同步更新语言切换入口、使用指南和公开介绍，免得某个语种只剩空标题或过时说明。

## 8. 性能调优与文件整理

做优化前先找真热点：重点盯住高频 `on_actions`、全图/全国遍历、深层嵌套循环、每帧重算的显示条件以及超大动态纹理。结果只随状态改变时，用事件驱动或缓存来替代轮询，并把缓存何时失效写透。

降频减负时守住原设计语义：别为了省几毫秒悄悄把“每日生效”改成“每周生效”。确实需要分批处理时，记录进度游标、设好单批上限，并确保玩家看到的反馈与设计一致。

整合碎片文件时，把同属一个解析目录、加载规则和生命周期的小文件按功能归拢；凡是承担加载顺序、兼容覆盖、代码生成或独立维护职责的拆分，原样保留。合并小文件主要换来清晰的目录结构和更利落的启动读盘，至于局内帧率能否改善，仍要靠实际性能剖析说话。

合并前逐一比对定义、命名空间、先后顺序、重复键和资源引用；遇到同键异值，先弄清业务意图再取舍。若文件由脚本生成，务必同步更新生成器，保证再次构建能稳定复现，所有手工修订都回到真正的数据源。

## 9. 排错从复现与完整证据起步

提报问题时交代五个要素：游戏版本、启用 Mod、触发操作、预期结果、实际现象。看日志要对准出事时段，按根因合并刷屏报错，先拔掉会阻断后续加载的解析与引用错误。别把崩溃前最后一行日志、旧运行的残留日志或拍脑袋的猜测当成定论。

遇到跨文件问题，从定义一路追到消费者，逐一核对作用域、状态、依赖与素材。把确定性缺陷、启发式线索、设计偏好和待证假设分栏写清，动刀始终对准已坐实的根因。

只有问题确有需要、工具就位且授权明确时，才升级到原生调试或转储分析，同时脱敏处理隐私信息；普通 `error.log` 排查绝不擅自演变成附加进程、装工具或抓完整内存。

## 10. 按风险选用恰到好处的验收

| 改动类型或证据 | 合适的验证方式 | 仍需留意的边界 |
| --- | --- | --- |
| 文案、注释、成熟模板微调 | 通读 diff，核对格式与占位符 | 仅覆盖文字层，不涉及运行时逻辑 |
| 脚本、引用、编码或资源接线 | 对改动文件跑静态校验与引用追踪 | 引擎内作用域、时序与 UI 交互需进游戏确认 |
| 离线模型、网页或静态图预览 | 核验规则运算、排版、像素与文件格式 | 原生输入、着色器渲染与存档行为需在游戏内复核 |
| 实机操作 | 在指定版本、播放集与场景下直接观察 | 仅代表本次实测组合，其他版本、旧档、联机或未走分支需另行确认 |

围绕真实失败风险挑最小充分的检查，能复用的有效证据直接复用。小改动通常 0–3 个关键观察点就够了；确实需要启动游戏时，在授权范围内选最短路径（当前会话、测试存档或新开局），并把准备与还原时间算进预算。修完 Bug 只做定向复验，不必机械重跑整套基线。

启动游戏只用来回答静态检查给不出答案的问题。手头没有桌面控制工具或你不想启动游戏时，直接标注“实机未验证”并附上简明手测步骤即可；每一次新改动都要对应自己的新证据，绝不拿旧测试记录充数。

## 11. 文档、Git 与交付

- **文档各司其职**：技术指南沉淀当前有效的架构、入口、状态、兼容与构建契约；开发日志记录某次改动的来龙去脉与验证结果。小改直接更新既有章节，别动不动新起一套文档。
- **Git 动作分清界限**：提交前先看工作区与暂存区 diff，妥善保留他人未完成的改动；资源更名、生成器与引用成套交付。提交、推送、打 Release 和上传 Workshop 是彼此独立的动作，严格按你的指令和实际远端/分支执行。
- **交付透明、公共文档干净**：收尾时说清完成了什么、验证到哪一步、还有哪些未实测边界，以及当前 Git 状态。对外公开的文档统一使用通用示例与占位路径，不混入私人目录、具体项目角色或旁人无从复核的私下记录，并按规保留来源与许可声明。

## 12. 可直接套用的实战请求模板

**只评估可行性**

> 评估在当前 Mod 中制作一个可保存进度的经营面板是否可行：说明输入接口、状态归属、读档与暂停行为、性能上限以及最小验证方案。先只出分析，暂不改文件，也不启动游戏。

**修复既有 Bug**

> 这个事件在第二次打开时会重复发奖励。请沿着入口、玩家文案和状态生命周期查清原因，修掉重复领取同时兼容旧存档进度。只验证受影响分支，保持其他奖励数值不变。

**整理碎片文件**

> 把最近新增的碎片文件按功能归类整合，保留所有 ID、加载顺序与兼容边界，同步更新生成器和引用。给我一份合并前后的路径映射与内容等价核对结果，保持玩法完全不变。

**替换素材并同步多语言**

> 用我提供的原图替换这个界面背景，按现有消费控件尺寸等比适配，沿用原设计的补边方式并保留原件。同步更新所有支持语言的说明，检查最长文本与新增资源路径，最后汇总输出规格和检查结果。

**准备交付与推送**

> 把这轮完成的修复整理成更新说明，把已实测和未实测的边界分开写清。核对暂存区范围后提交并推送到当前项目配置的目标分支，保留工作区里无关的本地改动；本次先不发 Release 或上传 Workshop。
